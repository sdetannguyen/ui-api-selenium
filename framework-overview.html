ui-api-selenium

A Java-based test automation framework for UI and API tests. Built for team adoption — not just personal use.

Java 8 Selenium 4.6 RestAssured 5.3 TestNG 7.4 Maven 3.8 WebDriverManager 6.1 Jackson 2.17

Structure

Three strict layers. Each layer has one job and depends only on the layer below it.

Layer 1

Infrastructure common/

  • AutomationConfigs (singleton config)
  • DriverManager / DriverFactory
  • DriverStorage (ThreadLocal)
  • BaseAPIs (HTTP wrappers)
  • Cleanup (teardown)
Layer 2

Abstraction pom/ apis/

  • ReqresHomePage
  • PracticeAutomationLoginPage
  • UsersApiClient
  • JsonPlaceholderUser (POJO)
Layer 3

Tests acceptance_test/ api_test/

  • ReqresHomeTest (UI)
  • UsersApiTest (API)
  • Thin AAA specs only
  • No Selenium or HTTP calls

src/test/java/ common/ ← infrastructure layer (shared, opinionated core) driver/ ← WebDriver lifecycle and thread isolation apis/ ← HTTP base client and service-specific clients utils/ ← Selenium actions, JSON, sorting helpers cleanup/ ← test data teardown AutomationConfigs.java ← singleton config reader acceptance_test/ ← UI abstraction + test layer pom/ ← page objects BaseTest.java ← TestNG hooks, driver initialisation ReqresHomeTest.java ← UI test specs api_test/ ← API abstraction + test layer BaseTest.java ← TestNG hooks, API client initialisation UsersApiTest.java ← API test specs unit/ ← infrastructure unit tests pojos/ ← typed response models parallelRun.xml ← TestNG parallel execution suite unitTests.xml ← TestNG unit test suite (CI default) src/resources/ config.properties ← environment config

Intent

This framework is designed as a platform, not a script collection. The goal is that any engineer on a team — not just QA — can contribute tests without specialised knowledge. The opinionated common/ core enforces consistency; the edges (page objects, API clients) are where teams extend freely.

The secondary intent is to demonstrate scalability thinking: ThreadLocal isolation for parallel safety today, the same isolation principle applies in a Kubernetes pod-per-test setup tomorrow.

What Works Well / What Doesn't

Works Well

  • ThreadLocal driver isolation — parallel tests never collide
  • Typed API responses — assertions are refactor-safe
  • Clean layer separation — test code reads like plain English
  • Fast CI default — unit tests run in <2s, no browser needed
  • Security scanning built in from the start
  • Config externalised — no hardcoded URLs in test code

Doesn't Work Well

  • E2E tests not in CI — real Chrome can't run on GitHub Actions without Xvfb setup
  • Selenium 4.6 is behind — CDP warnings on Chrome 148, latest is 4.x
  • No headless toggle in config — has to be hardcoded
  • AutomationConfigs reads file on every call — no caching
  • No retry logic for flaky UI interactions
  • Test coverage is thin — 2 UI and 4 API tests total

What's Missing

  • High E2E tests in CI — UI tests run locally only. CI needs headless Chrome + Xvfb, or switch to a remote grid (Selenium Grid, BrowserStack).
  • High Retry mechanism — No handling for transient failures (network blips, slow page loads). A @Retry listener or IRetryAnalyzer is standard in production frameworks.
  • Medium HTML test reports — Surefire XML only. Allure or ExtentReports would give visual history, screenshots on failure, and trend charts.
  • Medium Screenshot on failure — No hook captures a screenshot when a UI test fails. Debugging failures in CI is blind without it.
  • Medium Headless mode config — Hardcoded headed Chrome. Should be a config flag so CI runs headless and local runs headed.
  • Low Multi-environment support — config.properties is single-environment. A proper setup uses per-env property files (config-qa.properties, config-staging.properties) selected by a Maven profile.
  • Low Logging — No SLF4J binding, only console output. A structured logger would make CI failures easier to trace.

Selenium vs Playwright

Selenium (this repo)

  • Cross-browser: Chrome, Firefox, Safari, Edge, IE
  • Cloud grid ready: BrowserStack, SauceLabs, Selenium Grid
  • Mature ecosystem, vast community, 15+ years of answers on SO
  • Java — same language as backend teams
  • Explicit waits, familiar mental model
  • Standard in enterprise QA hiring

Playwright (TypeScript)

  • Built-in auto-wait — almost no flakiness by default
  • Trace viewer — visual replay of every test failure
  • Codegen — record interactions to generate test code
  • Native API testing in the same test file
  • Faster execution, better debugging DX
  • Modern choice for greenfield projects
When to choose Selenium: Enterprise teams with existing Java infrastructure, cross-browser requirements, or cloud grid needs. When the team already knows Java and you need to onboard without a language switch.

When to choose Playwright: Greenfield projects, TypeScript/JS teams, when developer experience matters most, or when you want the fastest path to reliable end-to-end tests. For most modern teams starting fresh, Playwright is the better default.

Mục tiêu thiết kế

Framework được xây dựng như một nền tảng (platform), không phải tập hợp script. Mục tiêu là mọi engineer trong team — không chỉ QA — đều có thể đóng góp test mà không cần kiến thức chuyên sâu. Package common/ có tính opinionated để đảm bảo nhất quán; các phần mở rộng (page objects, API clients) là nơi từng team tự do thêm.

Mục tiêu thứ hai là thể hiện khả năng scale: ThreadLocal đảm bảo isolation cho parallel test hôm nay — nguyên lý tương tự áp dụng cho kiến trúc pod-per-test trên Kubernetes ngày mai.

Điểm tốt / Chưa tốt

Điểm tốt

  • ThreadLocal driver isolation — parallel test không xung đột nhau
  • API response có kiểu — assertion an toàn khi refactor
  • Phân tầng rõ ràng — test code đọc như văn xuôi
  • CI mặc định chạy nhanh — unit test chạy <2s, không cần browser
  • Security scanning được tích hợp từ đầu
  • Config tách khỏi code — không có URL hardcoded trong test

Chưa tốt

  • E2E test chưa chạy được trên CI — cần Xvfb hoặc remote grid
  • Selenium 4.6 đã cũ — có warning CDP trên Chrome 148
  • Không có toggle headless/headed trong config
  • AutomationConfigs đọc file mỗi lần gọi — không cache
  • Không có retry logic khi UI test bị flaky
  • Coverage còn mỏng — chỉ có 2 UI và 4 API test

Còn thiếu gì

  • Cao E2E test trên CI — UI test chỉ chạy được local. CI cần headless Chrome + Xvfb, hoặc kết nối remote grid (Selenium Grid, BrowserStack).
  • Cao Retry mechanism — Không xử lý được lỗi tạm thời (mạng chập, trang load chậm). Cần thêm IRetryAnalyzer của TestNG cho framework production.
  • Vừa HTML test report — Hiện chỉ có XML Surefire. Allure hoặc ExtentReports sẽ cho lịch sử chạy trực quan, screenshot khi fail, biểu đồ xu hướng.
  • Vừa Screenshot khi fail — Không có hook chụp màn hình khi UI test thất bại. Debug trên CI không có ảnh là gần như mù.
  • Vừa Config headless mode — Chrome mặc định headed. Nên thêm flag trong config để CI chạy headless, local chạy headed.
  • Thấp Multi-environment — config.properties chỉ cho một môi trường. Nên dùng profile Maven với config-qa.properties, config-staging.properties riêng.
  • Thấp Logging — Không có SLF4J binding, chỉ có console output. Logger có cấu trúc giúp trace lỗi trên CI dễ hơn nhiều.

So sánh với Playwright

Selenium (repo này)

  • Đa browser: Chrome, Firefox, Safari, Edge, IE
  • Tích hợp cloud grid: BrowserStack, SauceLabs, Selenium Grid
  • Hệ sinh thái trưởng thành, cộng đồng lớn, 15+ năm
  • Java — cùng ngôn ngữ với backend team
  • Explicit waits, quen thuộc với QA truyền thống
  • Tiêu chuẩn trong tuyển dụng QA enterprise

Playwright (TypeScript)

  • Auto-wait có sẵn — gần như không bị flaky mặc định
  • Trace viewer — xem lại từng bước khi test fail
  • Codegen — record tương tác để sinh code test tự động
  • Test API native trong cùng file test với UI
  • Chạy nhanh hơn, DX tốt hơn, debug dễ hơn
  • Lựa chọn hiện đại cho project mới
Khi nào nên chọn Selenium: Team enterprise có hạ tầng Java sẵn, yêu cầu đa browser, hoặc cần kết nối cloud grid. Khi team đã quen Java và không muốn chuyển đổi ngôn ngữ.

Khi nào nên chọn Playwright: Project mới, team TypeScript/JS, khi developer experience là ưu tiên hàng đầu, hoặc khi muốn viết end-to-end test ổn định theo cách nhanh nhất. Với hầu hết team hiện đại bắt đầu từ đầu, Playwright là lựa chọn tốt hơn.
